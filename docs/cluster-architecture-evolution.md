## 角色 ↔ 代码组件总对照

| 餐厅角色 | 代码组件 | 所在位置 |
|----------|----------|----------|
| 收银台 | FastAPI 路由 | `src/octop/api/routers/` |
| 厨房（基线时） | AgentManager → HarnessAgentRuntime | `infra/agents/manager.py` |
| 厨师岗位说明书 | AgentExecutor 协议 | `infra/agents/executor.py` |
| 原班人马厨师 | InProcessExecutor（默认实现） | `infra/agents/executor.py` |
| 中央厨房 | AgentWorker + HarnessLocalExecutor | `infra/agents/remote.py` |
| 中央柜台 | PostgreSQL（唯一枢纽） | 复用，无新增中间件 |
| 取餐口（任务队列） | procrastinate / ProcrastinateTurnQueue | `infra/agents/remote.py` |
| 进度照墙 | turn_events 表 | PG |
| 铃铛（喊人） | pg_notify | PG |
| 桌号锁（同桌不上两份菜） | 队列锁 `octop-turn:{agent}:{thread}` | procrastinate |
| 大门闸机 | nginx 负载均衡 | `docker/cluster-lb.conf` |
| 值班班长 / 钥匙 | LeaderRunner / PG advisory lock | `infra/cluster/leader.py` |
| 广播线 | NotifyHub（每进程 1 根 LISTEN） | `infra/agents/remote.py` |
| 查岗线 | TurnFetchPool（8 根连接轮流用） | `infra/agents/remote.py` |
| 大扫除 | prune_turn_events（分批 DELETE） | `infra/agents/remote.py` |
| 岗位牌（三种身份） | BackgroundGate | `infra/cluster/leader.py` |
| 闹钟 | CronManager（APScheduler） | `infra/cron/` |
| 总机 | Gateway（ChannelManager + WebSocketHub） | `infra/gateway/` |
| 保洁 | 知识恢复 | `infra/` |
| 账本 | SQLite(WAL) 或 PG 控制面 | `infra/db/` |
| 文件柜 | 本地 workspace `~/.octop/agents/<id>/` | `infra/backend/` |

## 第 1 幕 · 改造前：一家啥都干的小店（基线全景）

commit：`dc07c650`（2026-09-24）

**为什么看它**：这是还没动手改的老样子——所有活都在一个进程里干。

```text
  你（浏览器 / 微信钉钉 / 命令行）
        │
        ▼
┌─ 一间屋子 = Octop 单进程 ─────────────────────────
│   收银台 = api/routers（接待你点单）
│   厨房   = AgentManager → HarnessAgentRuntime
│            （AI 对话就在这跑，和收银台焊在一起，
│              收银台一转身就能喊厨房：同进程直调）
│   闹钟   = CronManager（APScheduler 定时任务）
│   总机   = Gateway（IM 通道 + WebSocketHub）
│   保洁   = 知识恢复
│
│   账本   = SQLite(WAL) / PG 直连（infra/db/）
│   文件柜 = 本地 workspace（infra/backend/）
└──────────────────────────────────────────────────

  ▼ 基线问题：想多开几家店分担客流？开可以 ——
     但每家店都会响同一个闹钟、都抢着回总机
     → 同一件事被干 N 遍，乱套。
     所以现在：只能开一家，客满了就只能等。
```

**一句话**：厨房焊死在收银台旁边，想扩容只能把整家店复制，复制了又打架。

## 第 2 幕 · 收银和厨房分家（`427b1ff2` · 阶段 2）

**为什么改**：客流大了，收银和厨房必须分开，各自想加人就加人。

```text
  你（浏览器 / IM）
        │
        │ ①点单
        ▼
┌─ 前台店（api 节点）★新增分家 ─────────────────────
│   收银台 = api/routers（只接单，不做菜）
│      │
│      ▼ 构造器注入
│   ★厨师岗位说明书 = AgentExecutor（infra/agents/executor.py）
│      ├─ InProcessExecutor
│      │    原班人马就地做菜（默认模式，行为 = 原版）
│      └─ ★RemoteExecutor（remote 模式启用）
│           只接单：把小票放进中央柜台的取餐口
│           （OCTOP_EXEC_MODE=remote + OCTOP_QUEUE_DSN）
│           ★前台不再预启动任何厨师 → 内存 O(1)
│
│   闹钟 CronManager / 总机 Gateway / 保洁
│   （★这一幕还没动它们 —— 多前台会打架，下一幕收编）
│
│   ④上菜：盯着进度照墙，有新照就推给你
└──────────────────────────────────────────────────
        │                       ▲
        │ ①下单小票，入取餐口     │ ②小票到了摇铃铛
        ▼                       │ （pg_notify）叫前台看照
┌─ ★中央柜台 = PostgreSQL ─────────────────────────
│   · 取餐口   = procrastinate 任务队列
│   · 进度照墙 = turn_events 表
│   · 铃铛     = pg_notify
└──────────────────────────────────────────────────
        ▲
        │ ③现炒现装盘：每 50ms 拍一张进度照贴上照墙
        │
┌─ ★中央厨房（agent-worker ×N）─────────────────────
│   启动命令：octop agent-worker
│   · 厨师 = ★HarnessLocalExecutor（菜真正在这炒）
│   · ★warmup 预热：开工前先烧热锅
│     （防 checkpointer 索引死锁）
└──────────────────────────────────────────────────

  ▼ 相对第 1 幕的差异：厨房搬出屋子成为独立中央厨房；
     账本升级成中央柜台（多了取餐口/进度照墙/铃铛三个窗口）；
     闹钟/总机/保洁原地没动 —— 留给下一幕。

  靠谱的小设计（都在 infra/agents/remote.py）：
  · 同一桌不上两份菜 —— 桌号锁 octop-turn:{agent}:{thread}
  · 客人喊「不要了」—— pg_notify 传话厨房停火（取消跨进程）
  · 厨房 30 分钟没动静 —— 前台放弃等（TurnStreamReader 1800s 看门狗）
```

**改了什么（人话版）**：
1. 定了「厨师岗位说明书」（`AgentExecutor` 协议，`infra/agents/executor.py`）：5 个调用点改成注入式，原班人马 `InProcessExecutor` 照旧干，也可换成 `RemoteExecutor`。
2. 前台从此不养厨师：remote 模式下 api 不预启动 agent，内存 O(1)。
3. 新命令 `octop agent-worker`（`cli/commands/agent_worker.py`）一条命令起一个中央厨房。
4. 唯一新依赖 procrastinate>=3.8；柜台还是那个 PG，**零新增中间件**。

## 第 3 幕 · 开分店 + 选值班班长（`1a2c972a` · 阶段 3）

**为什么改**：前台店要开两家以上才扛得住；但闹钟、总机这些活，全公司只需要一个人干。

```text
  你 ──► ★大门闸机 = nginx（docker/cluster-lb.conf）
                · SSE 无缓冲 · Last-Event-ID 断流续传
                │
        ┌───────┴────────┐
        ▼                 ▼
┌─ ★前台 A（api 副本 1）───────────────────────────
│   ★抢到钥匙 = 值班班长
│   （LeaderRunner 抢 PG session 级 advisory lock，
│     infra/cluster/leader.py）
│   干杂活（★全集群只此一份）：
│     · 闹钟 CronManager   · 总机 Gateway
│     · 主动关怀           · 保洁（知识恢复）
│   ★顺带管大扫除：prune_turn_events
│    （进度照墙定期清，不再贴满）
└──────────────────────────────────────────────────
┌─ ★前台 B（api 副本 2）───────────────────────────
│   ★光接单，不干杂活
│   ★A 一挂 → 接管循环秒顶上（客人无感）
└──────────────────────────────────────────────────
        │
        ▼
  ★电话线改革（PG 连接数 70 → 13，均有界）：
  · 广播线 ★NotifyHub：每前台进程 1 根 LISTEN，
    按 job 喊人；丢通知就轮询兜底（慢点但不出错）
  · 查岗线 ★TurnFetchPool：8 根连接轮流用
    （以前每个等菜的客人自己拉 1 根 → 客一多线就爆）
        │
        ▼
┌─ 中央柜台 = PostgreSQL ──────────────────────────
│   ★advisory lock（班长钥匙）+ 取餐口 + 进度照墙
└──────────────────────────────────────────────────
        ▲ 取小票
        │
┌─ ★中央厨房 ×2（agent-worker ×N，随便加）───────────
│   ★leader=False：纯做饭，不抢钥匙，
│     不跑任何后台（run_background=False）
└──────────────────────────────────────────────────

  ▼ 相对第 2 幕的差异：前台可以开分店了（大门闸机分流）；
     上一幕遗留的闹钟/总机/保洁终于被收编——只有班长跑；
     电话线从「每人一根」变成「全场共用几根」。
```

**改了什么（人话版）**：
1. 新增 `infra/cluster/leader.py`（`LeaderRunner`/`LeaderHandle`）：server.py 把 4 项后台单例挂到班长，全集群恰好跑一份。
2. 厨房认身份：`octop agent-worker` 加 `run_background=False`，纯执行、永不选主。
3. 电话线有界（NotifyHub + TurnFetchPool）+ 冷启动加锁（`_ensure_open` asyncio.Lock）+ 大扫除，PG 压力收敛。
4. 开店工具：`docker/docker-compose.cluster.yml`（PG+MinIO+api×2+worker×2+nginx）一键起全套。

## 第 4 幕 · 班长交接流程补漏（`14be3500` · 评审修复）

**为什么改**：评审发现交接班有隐患——拓扑不变，把流程做可靠。

```text
  你 ──► 大门闸机 = nginx（不变）
                │
        ┌───────┴────────┐
        ▼                 ▼
┌─ 前台 A = 值班班长 ──────────────────────────────
│   抢钥匙做杂活（advisory lock，不变）
│   ★交接串行化：transition 锁 ——
│     前任把动作做完，新人才开始；
│     transition 任务持强引用（防 GC）；
│     _handles_running 保证 stop 恰好一次
│   ★钥匙线保活：TCP keepalive（idle 30s×3）
│     → 半开连接 ~1 分钟检出；
│     心跳 SELECT 1 加 wait_for 超时（3×poll）双保险
└──────────────────────────────────────────────────
┌─ 前台 B = 光接单（不变，接管流程同样加固）───────────
└──────────────────────────────────────────────────
        │
        ▼
  ★接线收纳：新增 ★BackgroundGate（infra/cluster/leader.py）
    server.py 只剩 4 行 gate.route(...)，
    集群逻辑全部收进 octop.infra.cluster 包
    → 上游合并冲突极小
        │
        ▼
  电话线（广播线 / 查岗线，不变）
  ★查岗线坑位归还：建连失败回滚预留槽位
    → 池容量在连接风暴下不再永久缩水
        │
        ▼
┌─ 中央柜台 = PostgreSQL（不变）────────────────────
└──────────────────────────────────────────────────
        ▲ 取小票              ▲ 大扫除
        │                    │★改小批量：每批 5000、autocommit
        │                     （老店首次大扫除不卡死）
┌─ 中央厨房 ×2（不变：纯做饭，不抢钥匙）───────────────
└──────────────────────────────────────────────────

  ▼ 相对第 3 幕的差异：拓扑一格没动。变的是
     班长交接流程（串行 + 保活）、代码摆放（gate 收纳）、
     电话线/大扫除的小加固。
```

**改了什么（人话版）**：
1. 交接班串行化（transition 锁 + 强引用 + stop 恰好一次）。
2. 钥匙会话加 TCP keepalive + 心跳超时，假死 1 分钟内检出，failover 更快更准。
3. 新增 `BackgroundGate`：server.py 接线收敛成 4 行，集群逻辑全收进 cluster 包。
4. 查岗线坑位归还 + 大扫除小批量，老店首次大扫除不卡死。

## 第 5 幕 · 补三个大窟窿（`61ed6302` · P0/P1 修复）

**为什么改**：评审揪出几个真窟窿：厨师塌了没人管、喊停没人听、身份分不清。

```text
  你 ──► 大门闸机 = nginx（不变）
                │
        ┌───────┴────────┐
        ▼                 ▼
┌─ 前台 A = 值班班长（不变：抢钥匙做杂活，
│   交接已串行、钥匙线有保活）───────────────────────
│   ★岗位牌 = BackgroundGate.enabled，三种身份写死：
│     单机店   → 就地全跑（老行为不变）
│     集群前台 → 抢到钥匙才跑
│     ★集群厨房 → 什么都不跑，只做饭
│      （以前厨房被误判成单机店 → N 个厨房
│        全在响闹钟/接总机 → N+1 遍！已修）
└──────────────────────────────────────────────────
┌─ 前台 B = 光接单（不变）──────────────────────────
└──────────────────────────────────────────────────
        │
        ▼
  电话线（广播线 / 查岗线）
  ★查岗线取消安全：捕获 BaseException ——
    取消不漏坑位，先还坑位+唤醒哨兵再关连接
    → 连点 8 次取消也不瘫痪
  ★取消改走 _CancelNotifier（常驻异步连接），
    不再卡事件循环 3 秒；_cancel_loop 带退避重连
        │
        ▼
┌─ 中央柜台 = PostgreSQL ──────────────────────────
│   ★铃铛现在也传「喊停」：pg_notify → 厨房停火
│    （以前 WS cancel 和 slash /stop 只能停本地厨师，
│      菜在中央厨房时喊了白喊 —— 本幕接通）
│     统一入口：executor.cancel_turn（executor.py）
└──────────────────────────────────────────────────
        ▲ 取小票              ▲ ★点名自愈
        │                    │  AgentWorker._stalled_loop
        │                    │  （60 秒一轮）：
        │                    │  工牌消失（人没了）→ retry_job
        │                    │  重派，从断点续做；
        │                    │  >2100s 的 doing 兜底；
        │                    │  卡单恢复 RTO ≤ 2 分钟
┌─ 中央厨房 ×2 ────────────────────────────────────
│   ★开工即预热（prestart_agents=True）：
│     第一单不再等冷启动
└──────────────────────────────────────────────────

  ▼ 相对第 4 幕的差异：拓扑还是没动。补上了三个真窟窿：
     厨房塌了有人接单（自愈点名）、喊停全链路通
     （你 → 前台 → 铃铛 → 厨房）、厨房认清身份（岗位牌）。
```

**改了什么（人话版）**：
1. 僵尸订单自愈：`_stalled_loop` 每分钟点名，崩溃厨师的订单 2 分钟内被接手。
2. 「停止生成」在集群下真正生效（`cancel_turn` helper 统一两条取消路径）。
3. `BackgroundGate.enabled` 三分支：厨房绝不再碰闹钟/总机（N+1 修复）。
4. 查岗线取消安全 + 取消链路重连/非阻塞 + 厨房预热。

## 第 6 幕 · 把「太热心」的自愈收一收（`efc958e1` · 缺陷修复）

**为什么改**：第 5 幕的自愈太积极——厨师只是做大菜做得久，就被当成塌了，订单被重复派。

```text
  你 ──► 大门闸机 = nginx（不变）
                │
        ┌───────┴────────┐
        ▼                 ▼
┌─ 前台 A = 值班班长（不变）────────────────────────
└──────────────────────────────────────────────────
┌─ 前台 B = 光接单（不变）──────────────────────────
└──────────────────────────────────────────────────
        │
        ▼
  电话线（广播线 / 查岗线，机制不变）
        │
        ▼
┌─ 中央柜台 = PostgreSQL ──────────────────────────
│   ★下队失败立刻报错：TurnEventPublisher.open()
│     移入 try —— 下单失败（PG 抖动/连接满）也经
│     publisher.fail 发哨兵；conn 为空时 best-effort
│     建独立连接发哨兵
│     → 客人马上知道「这单失败」，
│       不再对着进度照墙傻等 1800s 看门狗
└──────────────────────────────────────────────────
        ▲ 取小票              ▲ 点名（60 秒一轮，机制不变）
        │                    │
        │                    │ ★自愈规则收窄（retry_stalled_jobs_once）：
        │                    │   工牌消失（人真没了）→ 重派 ✓（保留）
        │                    │   做太久（>2100s）→ ★只监控、不重派
        │                    │    （worker 活着就不动手；
        │                    │      人真没了，点名照样兜住）
        │                    │ ★重派扫描逐小票容错：
        │                    │   一张小票 RAISE → 跳过继续，
        │                    │   不再一张卡住、整轮罢工
┌─ 中央厨房 ×2（不变：纯做饭，开工即预热）─────────────
└──────────────────────────────────────────────────

  ▼ 相对第 5 幕的差异：拓扑依旧没动。自愈从「太热心」
     变「精准」——大菜不会被炒两遍；坏消息当场送达；
     扫描不再被一张坏单拖垮。
```

**改了什么（人话版）**：
1. 自愈收窄：只有「确认人没了」才重派，「做得久」降级为只监控——大菜不会被炒两遍。
2. 下队失败立即发失败哨兵（fail-fast），用户不再白等半小时。
3. 重派扫描单作业容错，一张坏单不拖垮整轮。
4. 归档外部评审报告与后续计划（`docs/cluster-assessment-2026-09-25.md`、`cluster-implementation-plan-2026-09-25.md`）。

## 第 7 幕 · 改渠道，全店立刻知道（`df3221bf` · D2 渠道跨节点传播）

**为什么改**：以前在前台 B 加了个外卖渠道，账本上记了，但总机在班长（前台 A）手里——班长不知道这事儿，新渠道永远不接线；删渠道也一样，人走了电话还响。

```text
  你 ──► 大门闸机 = nginx（不变）
                │
        ┌───────┴────────┐
        ▼                 ▼
┌─ 前台 A = 值班班长 ───────────────────────────────
│   ★耳朵 = ChannelChangeWatcher
│     （1 根专线 LISTEN，断了自动重连）
│     铃铛一响 → 重新翻账本接线
│     （reload_channels_from_db，翻几遍都不出错）
└──────────────────────────────────────────────────
┌─ 前台 B = 光接单 ─────────────────────────────────
│   ★嘴 = ChannelChangeNotifier
│     （1 根常驻连接，懒打开，坏了下次自动重连）
└──────────────────────────────────────────────────
   │ 前台 A/B 改完账本后都摇铃        │
   ▼                                ▼
┌─ 中央柜台 = PostgreSQL ──────────────────────────
│   账本 channels 表 = 事实源（没变）
│   ★新装一只「渠道变更铃」＝ pg_notify
│     专线（octop_channel_changes）
│     → 前台改一行 = 摇一次铃 = 班长翻一次账本
│     → 漏摇也不怕：下次变更照样兜住，
│       铃响时翻账本永远翻到最新真相
└──────────────────────────────────────────────────
        ▲ 取小票              ▲ 点名（不变）
        │                    │
┌─ 中央厨房 ×2（不变：纯做饭）──────────────────────
└──────────────────────────────────────────────────

  ▼ 相对第 6 幕的差异：柜台上多一只「渠道变更铃」，
     班长长了耳朵，前台 B 长了嘴——改渠道不再只改
     账本没人理。铃是通知、账本是真相：通知丢了
     只慢一点，不会错。
```

**改了什么（人话版）**：
1. 任何一个前台增/删/改渠道，班长立刻重新翻账本接线（`create/update/delete_channel` 落库后 `pg_notify`，班长侧 `ChannelChangeWatcher` 收铃即 `reload_channels_from_db`）。
2. 通知是尽力而为：DB 行永远是事实源，reload 幂等——铃丢了只是慢一拍，下次变更照样收敛到最新状态。
3. 接线全部收进 `infra/cluster/channel_bus.py`（发布端对齐 `_CancelNotifier`、监听端对齐 `NotifyHub`，各 1 根连接，O(节点)）；worker 厨房不装耳朵。
4. 部署形态拍板：以 stage3（remote）为准，目标 = 集群体验与单机体验一致（`cluster-implementation-plan` 岔路一已记录）。

## 第 8 幕 · 开店装修排好队（`a03d6882` · D5 迁移跨进程锁）

**为什么改**：`--scale` 一口气开 3 家分店时，三家同时装修（跑数据库迁移）——重复建桌子还算运气好，`published_experts` 装修队会整屋重建，两家同时拆就塌了。

```text
  你 ──► 大门闸机 = nginx（不变）
                │
        ┌───────┴────────┐
        ▼                 ▼
┌─ 前台 A = 值班班长（不变，耳朵还在听渠道铃）─────────
└──────────────────────────────────────────────────
┌─ 前台 B = 光接单（不变，嘴还在摇铃）─────────────────
└──────────────────────────────────────────────────
        │
        ▼
  电话线（不变）
        │
        ▼
┌─ 中央柜台 = PostgreSQL ──────────────────────────
│   ★新立一块「装修牌」＝ 会话级 advisory lock
│     （MIGRATION_LOCK_KEY=918273648，新号牌，
│       与队列 645 / 热身 646 / 选主 647 错开）
│     → 谁想动账本结构，先摘牌独占；
│       一家装修时其余排队等，装完自动轮到下一家
│     → 牌子挂在专用连接上：进程崩 = 连接断 =
│       牌子自动归位，不会卡死队伍
│     ★账本结构（channels/turn_events/小票…）从此
│       只被一家改，其余家只读等结果
└──────────────────────────────────────────────────
        ▲ 取小票              ▲ 点名（不变）
        │                    │
┌─ 中央厨房 ×2（不变）──────────────────────────────
└──────────────────────────────────────────────────

  ▼ 相对第 7 幕的差异：柜台上立了「装修牌」——拓扑没动，
     但并发开店从「三家抢着装修」变「排队装修」。
     SQLite 单机店没有这个问题（本来只有一个写字的），
     行为保持原样。
```

**改了什么（人话版）**：
1. `run_migrations` 在 PG 上先持 advisory 锁再动手（`MIGRATION_LOCK_KEY=918273648`），覆盖全部 9 个调用点（server 启动 / CLI / 备份恢复 / rebind）。
2. 锁挂在一根专用池连接上、`finally` 释放——迁移中途崩了，锁随连接断开自动归位，不产生死锁残留。
3. 评审点名的 `_ensure_published_experts_schema` 并发整表重建随之被串行化（它只在迁移体内被调用）。
4. SQLite 后端行为完全不变（WAL 单写者，无并发窗口）。
5. 后来（round2 评审 D5）排队方式升级：从「傻等装修牌空出来」改成 `pg_try_advisory_lock` 轮询——等的店每 5 秒喊一嗓子「还在等」（等待日志），等满 10 分钟就放弃报错，而不是无限期假装没死。

## 第 9 幕 · 换收银员，订单不断流（`c4be23b5` · D3 在途回合续接）

**为什么改**：以前你的菜做到一半，接待你的收银员倒了（api 节点崩溃/滚动升级）——厨房还在做（worker 继续跑、进度照还在拍），但没人接盘子：后半场直播黑屏，客人只看到一半。

```text
  你 ──► 大门闸机 = nginx（不变）
                │
        ┌───────┴────────┐
        ▼                 ▼
┌─ 前台 A = 值班班长（原收银员倒了也不怕）─────────────
│                    ┌─ 前台 B ──────────────────────
└────────────────────┤   ★新端点 =「续播窗口」
   任意一家前台都能开 │   GET .../turn/stream
                      │   查点名牌 → 对同一单重新开流
   ★「点名牌」= octop_turn_active_jobs 表
     （柜台上新增：thread → 正在做的 job）
     厨房一开工就挂牌，做完/做砸就摘牌
     ——哪家的前台倒了，另一家照名牌找到这一单
└──────────────────────────────────────────────────
        │ 认名牌续播                │
        ▼                          ▼
┌─ 中央柜台 = PostgreSQL ──────────────────────────
│   ★进度照墙从第一张重放（seq 0 回放）：
│     TurnStreamReader 重开即从头读
│     turn_events，补齐崩溃前+崩溃中+之后的画面
│   ★直播唤醒线全店共用（NotifyHub 本就跨节点
│     LISTEN）——前台 B 能收到厨房的实时摇铃
│   事实源不变：事件表一行不少，谁读都一样
└──────────────────────────────────────────────────
        ▲ 取小票              ▲ 点名（不变）
        │                    │
┌─ 中央厨房 ×2（不变）──────────────────────────────
│   ★开工先挂点名牌（claim），收工必摘牌（clear，
│     按 job 守卫——不摘掉排队新单的牌子）
└──────────────────────────────────────────────────

  ▼ 相对第 8 幕的差异：柜台加「点名牌」，厨房挂牌/
     摘牌，前台新开「续播窗口」。崩溃前后台看到的是
     同一单的完整直播，而不是前半场黑屏。
```

**改了什么（人话版）**：
1. 厨房开工即把「thread → job」写进柜台点名牌（`octop_turn_active_jobs`），收工必摘；牌子丢了只丢续播入口，不影响做菜。
2. 任何 api 节点凭点名牌找到在途 job，`RemoteExecutor.attach()` 从 seq 0 重放事件 + 共享 NotifyHub 跨节点唤醒续流——原节点死了，流由别人接管。
3. 新端点 `GET .../turn/stream`：浏览器/新节点重连即续播同一单（SSE chunk/done/error 帧）。
4. 边界（诚实交代）：续接是**裸 chunk 流**；thread_messages 投影与轨迹落库仍依赖原读端，投影级续接列为后续工作（`production-ha.md` §2.1 同步修改）。

## 第 10 幕 · 大菜做糊了就报废，不占灶（`49cff993` · D15 回合运行时上限）

**为什么改**：厨师没晕倒（心跳正常）、但一道菜卡死了（LLM 上游 hang / 工具永不返回）——灶台被永远占住，这个订单后面的菜全排不上。点名环只管「人没了」，管不了「人活着但卡死」；重派又怕炒两遍。

```text
  （全景拓扑不变：闸机 / 前台 A·B / 柜台 / 厨房 ×2）
        │
        ▼
┌─ 中央厨房 ×2 ────────────────────────────────────
│   ★灶台计时器 = 回合运行时上限（2100s）
│     每道菜开炒即计时：
│     正常出锅 → 照旧
│     ★超时 → 判这道菜报废（不重做，杜绝双跑）：
│       发「做糊了」哨兵给前台（读者马上知道，
│       不用等 1800s 看门狗）
│       → 作业标记失败 → 该订单的锁释放
│       → 后面的菜立刻能上灶
│   ★与点名环分工（注释已改对）：
│     人没了（心跳停跳）→ 点名环重派，断点续做
│     人活着但卡死 → 灶台计时器判死报废，不重做
└──────────────────────────────────────────────────

  ▼ 相对第 9 幕的差异：拓扑没动。厨房多了一个灶台
     计时器——「卡死」从无解变「最多 35 分钟必解锁」。
```

**改了什么（人话版）**：
1. `_execute_turn` 用 `asyncio.wait_for` 给每回合设 2100s 运行时上限（可配，`None` 关闭）；超时 → 错误哨兵 → 作业判失败 → 线程锁释放。
2. 判死不重派——无双跑窗口（procrastinate 3.10 无 `job_timeout`，评审建议的"组件自带"经核实不成立，自建）。
3. 修正 `_stalled_loop` docstring 与 `TURN_JOB_MAX_RUNTIME_SECONDS` 注释：假活兜底归属运行时上限，点名环只管真死。

## 第 11 幕 · 大门保安会赶客，也会认活人（`17476b64` · D9 LB 健康检查）

**为什么改**：门口保安（nginx）只是机械轮流传客——一家分店的收银员晕倒了，保安照样把 1/N 的客人往那儿领，客人站在关闭的窗口前干瞪眼（502）。而且分店「正在装修」（迁移中）或「电话线断了」（DB 断连）时，保安也分不清，照常放客进去。

```text
  （全景拓扑不变：闸机 / 前台 A·B / 柜台 / 厨房 ×2）
        │
        ▼
┌─ 大门保安（nginx LB）────────────────────────────
│   ★原来：名单写死一家店址，轮流传客，
│     谁倒下都照样往那儿领 → 1/N 客人吃闭门羹
│   ★现在：动态花名册（upstream + resolve）
│     --scale 开新分店自动登记，不用叫停重排
│   ★打烊登记（max_fails/fail_timeout）
│     连续两次敲窗没人应 → 记「暂时歇业」10 秒，
│     期间一个客人都不往那儿领（自动摘除）
│   ★改道重试（proxy_next_upstream）
│     客人还没进门就被拒 → 顺手领去下一家
│     （已下单的菜绝不重下单——非幂等不重放）
│   ★门口试音（readiness 探针 /api/health/ready）
│     每家分店门口装试音器，保安和总部都能问：
│     柜台通不通（DB 连通）？
│     装修完没（迁移版本对齐本构建）？
│     答不上来 = 「活着但不能服务」→ 不接客
└──────────────────────────────────────────────────

  ▼ 相对第 10 幕的差异：拓扑没动。大门保安从「瞎子
     轮盘」升级为「会摘除、会改道、会试音」——单店
     故障不再漏给客人。
```

**改了什么（人话版）**：
1. `cluster-lb.conf`：变量方案改 `upstream` 块——`resolve`（nginx ≥1.27.3 开源版）保留「扩缩容免重载」，`max_fails=2`/`fail_timeout=10s` 自动摘除失联副本，`proxy_next_upstream` 把连接失败/5xx 重试到健康副本；POST 仅在未发出时重试，消息不重复。
2. 新端点 `/api/health/ready`（无鉴权）：DB 连通 + 迁移版本匹配才 200，否则 503——「活着」与「能服务」从此分得清。
3. compose 给 api 加 readiness healthcheck（镜像无 curl，用 python urllib 探活）。

## 第 12 幕 · 换台听广播，节目不断（`574bf830` · D3 前端续接闭环）

**为什么改**：上一幕给了前台一个「续播窗口」（SSE 端点），但客人的收音机（dashboard）根本不会调到那个台——客人用的是对讲机（WebSocket）续订单，而对讲机只认「本店自己开的订单」。收银员晕倒后客人换一家店重连，新店对讲机说「这单不在我这儿」，客人以为菜没了。

```text
  （全景拓扑不变：闸机 / 前台 A·B / 柜台 / 厨房 ×2）
        │
        ▼
┌─ 前台 A·B（api ×N）──────────────────────────────
│   ★对讲机总台查点名牌（WS subscribe → D3 映射）
│     客人拿对讲机问「我的订单还在做吗」：
│     本店在做 → 照旧答「在做」
│     本店没做 → ★再查柜台上的点名牌：
│       名牌上有这个单 → 答「在做！」，
│       并把厨房的实况转播到对讲机里
│       （从第一句开始回放 + 铃铛唤醒续直播）
│     名牌上没有 → 答「没在做」（照旧）
│   ★一家店只开一路转播（单 relay 守卫）
│     两个客人同时问 → 只开一路转播，
│     大家听同一份，不会一人一份重复播
│   转播结束 → 对讲机里说「上齐了」（done），
│     点名牌摘掉，恢复安静
└──────────────────────────────────────────────────

  ▼ 相对第 11 幕的差异：拓扑没动。前台对讲机总台
     学会查点名牌并转播——客人换店重连，节目不断。
     前端一行没改（断线重连逻辑本就齐全）。
```

**改了什么（人话版）**：
1. `ws.py` subscribe 接入 D3 映射：本节点 hub 空闲时查 thread→job，命中则把 `attach` 的 chunk 流转发进 hub，并先报 `turn_status.active=true`——前端断线重连后自动继续渲染，**前端零改动**。
2. 单线程单 relay 守卫：并发 subscribe 不双份投递；结束推 `done` 并复位 idle；投递失败发 error 帧后收尾，不悬挂。
3. 单机模式（无 remote_executor）零改动。
