Octop 集群改造思路

一句话：别再造一个「什么都干」的大进程，而是按「这件事要不要全集群只有一份」把功能拆成三种角色，再让 Postgres 一个人当协调员。

对应阶段 3（多副本 + 选主）· 分支 feat/direct-portal-oidc

1为什么要拆：复制一份会把「只能有一份的东西」也复制

改造前所有功能都在一个进程里，想扩容只能整份复制 —— 于是定时任务、IM 轮询、主动关怀这些本该只跑一次的东西，被每个副本各跑了一遍。

2拆开之后靠什么连起来：让 Postgres 兼任协调员

三类角色在不同进程、可能在不同机器上，不能直接互相调用。方案的选择是不引入 Redis / ZooKeeper 这类新组件，直接用本来就有的 Postgres 当唯一协调员。

3拆开之后新增的三个麻烦，各自配一个机制

这三条是整个方案里最需要理解的部分 —— 它们都是「单进程时根本不存在、一拆开就冒出来」的问题。

4三个设计选择，以及各自的代价

  • 为什么不引入 Redis / ZooKeeper？少一个必须运维的组件、少一份要保证高可用的东西。代价是：Postgres 成了单点，生产必须上主备 + PITR。
  • 为什么选主用「会话锁」而不是带超时的租约？锁由数据库在连接断开时自动释放，天生不会脑裂、不用调超时参数。代价是：备节点接管要等一个轮询间隔（秒级）。
  • 为什么把「干活」单独拆成 worker？跑模型是最吃资源、最需要单独扩容的一层。代价是：取消、状态回传都变成了跨进程通信，得靠广播补回来。
一句话总结这套思路的取舍：用「所有节点都连同一个数据库」这一条硬约束，换来「不需要任何额外的分布式协调组件」。 规模在单库能扛住的范围内，这是性价比最高的方案；超过之后要换的就是数据库本身，而不是这套架构。
