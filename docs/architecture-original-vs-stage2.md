# 架构图：原版 vs 阶段 2 现状（ASCII 草图）

> 更新时间：2026-09-25。图 1 为原版；图 2 为阶段 2（RemoteExecutor + Procrastinate + DB/NOTIFY 流回传）之后的现状。
> 默认开关关闭时 = 图 1；`OCTOP_EXEC_MODE=remote` + `OCTOP_QUEUE_DSN` 时 = 图 2。

## 图 1 · 原版：单进程，全部住在一起

```
                          ┌─────────────────────────────────────────────┐
                          │            octop 单进程 (原样保留)           │
                          │                                             │
  用户 ──── HTTP/SSE ───►►│  api/routers ──► Gateway / cron / teams     │
  (浏览器/IM) ◄───────────┤       │                │                    │
                          │       │                ▼                    │
                          │       │        AgentManager ◄── 全量 agent  │
                          │       │        (内存 ∝ agent 总数)  预启动   │
                          │       ▼                │                    │
                          │  dashboard 静态资源    ▼                    │
                          │                 对话执行 (本进程 asyncio)    │
                          │                                             │
                          │   SQLite 或 PG (直连)     本地盘 workspace   │
                          └─────────────────────────────────────────────┘

  特点：一个进程包揽一切；后台单例 (cron/IM/知识恢复) 也在这一个进程里；
        想扩容只能整体复制，且复制后各节点会重复跑后台任务 → 不可水平扩展
```

## 图 2 · 阶段 2 之后：api 与 agent 分家，队列居中

```
            ┌───────────────┐        ┌──────────────────────┐
            │   api 节点    │        │   agent 节点 ×N      │
            │  (可横向复制)  │        │  (octop agent-worker)│
            │               │        │                      │
 用户 ─────►│ api/routers   │        │ AgentManager         │
 浏览器/IM  │ Gateway/cron  │        │  (按需启动, 不全量)   │
    ▲       │   │           │        │   │                  │
    │       │   ▼           │        │   ▼                  │
    │       │ RemoteExecutor│        │ HarnessLocalExecutor │
    │       │   │  ▲        │        │  (对话真正在这跑)    │
    │       └───┼──┼────────┘        └───┼──────────▲───────┘
    │           │  │ 6.读 chunk          │ 3.领取    │ 2.warmup
    │      1.入队│  │ (LISTEN+seq)        ▼          │  (预热索引)
    │           ▼  │            ┌────────────────────┴──┐
    │      ┌──────────────────────────────────────────┐  │
    │      │              PostgreSQL (唯一枢纽)         │  │
    │      │  ┌──────────────┐  ┌───────────────────┐ │  │
    └──────┼──┤ turn_events  │◄─┤ procrastinate_jobs│─┼──┘
     SSE   │  │ (chunk 落库) │  │  (任务队列/锁)     │ │
     推送   │  └──────▲───────┘  └────────▲──────────┘ │
            │         │ 5.NOTIFY 唤醒      │ 4.写 chunk │
            │         └───────────────────┘            │
            │  其余不变: 会话/轨迹/知识库/HITL checkpoint │
            └──────────────────────────────────────────┘

  走向：①api 把任务入队(同线程打锁→自动排队) → ②worker 启动预热 →
        ③worker 领任务本地执行 → ④chunk 每50ms落库+NOTIFY →
        ⑤api 被唤醒按序读取 → ⑥推给用户；取消走 pg_notify
```

## 关键区别（一句话版）

| 维度 | 原版（图 1） | 现状（图 2） |
|------|------------|------------|
| 执行位置 | 与 api 同进程，焊死 | 独立 worker 节点，可 ×N |
| api 节点内存 | ∝ agent 总数（全量预启动） | O(1)（不预启动） |
| 并发控制 | 进程内 asyncio.Lock | 队列锁（跨进程有效） |
| 结果回传 | 函数返回值 / 内存流 | chunk 落库 + NOTIFY |
| 新增组件 | — | 零（只用已有 PG） |
| 扩容方式 | 整体复制（会重复跑后台） | api 加副本、worker 加进程，各扩各的 |

## 边界说明

- 图 2 中 **cron、IM 网关等后台单例仍在 api 节点**（阶段 3 的角色拆分会处理）。
- worker 节点上的取消、HITL 恢复都经由 PG 传递，用户无感。
- 详细设计与联调证据见 `docs/microservice-scaling-1000.md` 与 `scripts/stage2/result.json`。
